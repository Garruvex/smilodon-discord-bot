# Character modules: operation and pilot

The implementation plan is [chat-believability-plan-2026-10-14.md](chat-believability-plan-2026-10-14.md). Modules and expanded conversation context default off. This guide describes a staged human review; automated tests cannot establish whether the character feels believable.

## Install and configure

For an isolated local classifier experiment, see [Laya evaluation](laya-local-evaluation.md).
It compares synthetic decisions without changing production provider routing.

Apply the normal database migrations before starting the new build. SQLite migration 0013 and PostgreSQL migration 0022 add nullable memory module ownership, separate memory identities and conversation-window retention. Ordinary facts remain ordinary facts. Use the normal database backup and deployment procedure.

If an older build fails during migration 0021 with `memory_id` text versus `memories.id` UUID, use the corrected build and rebuild/restart the bot containers. The correction makes alias references UUID in the original pending migration, schema and snapshot. PostgreSQL rolls back the failed migration; a retry keeps existing facts. No database reset or manual removal of migration history is needed. A plain-PostgreSQL recovery test reproduces the failed transaction and checks successful retry, preserved data and cascade deletion; set `POSTGRES_MIGRATION_TEST_DATABASE_URL` to a disposable test database to run it without pgvector.

The existing utility-provider chain performs reflections, canon extraction, fictional sketches and voice repair. For native contextual decisions using OpenAI's typed `/v1/decisions` API, set these instance-local values:

```dotenv
DECISION_MODE=decisions
DECISION_MODEL=gpt-6-luna
```

This route sends choice/predicate questions. It does not pass reasoning effort, verbosity or text-generation limits. Recipient, target, exchange link, evidence, action and contribution-kind choices remain subject to the existing source, confidence and participation guards. Native decisions produce no candidate prose: the normal reply provider generates text only after admission, and can still abstain when no useful grounded contribution can be written. Silent/reaction-only decisions do not invoke reply generation. Optional held-thought prose is not generated by the native path. Native failures remain failures; they do not silently fall back to a reasoning reply model.

Native adapter revision 2 binds fixed destinations in the application. After recipient/action classification, it binds a sole eligible destination or required exchange directly; multiple candidates use a second native choice call with event descriptions. Usage totals include both calls. A binding score of 1 denotes an application binding, not calibrated certainty that the bot was addressed. Recipient/action confidence still comes from classification. Optional evidence votes do not lower recipient confidence when the contract already binds the exchange evidence, and target confidence describes destination selection separately. The admission thresholds are unchanged. Contextual replay reports include `nativeAdapterRevision` so these results can be distinguished from earlier runs.

The native path requires `DECISION_API_KEY` or the instance's `OPENAI_API_KEY` and currently supports `gpt-6-luna`. Base URL defaults to the instance's `OPENAI_BASE_URL`. Enabling it requires deploying this build and updating the live instance configuration. With no explicit decision configuration, existing reply-provider routing remains unchanged. Legacy non-contextual decisions retain utility routing in native mode. The native health probe tests contextual capability.

For the previous OpenAI-compatible structured social provider, which combines decisions and candidate speech, use:

```dotenv
DECISION_MODE=chat_completions
DECISION_MODEL=your-decision-model
DECISION_BASE_URL=https://your-provider.example/v1
DECISION_API_KEY=your-key
```

The dedicated provider uses ordinary `/chat/completions` with structured JSON output. Candidate generation and self-rating happen in the same call; the confidence heuristics are uncalibrated. Direct/name requests retain an application-owned response obligation without optional model scoring. Omitted credentials/base URL use the instance's `OPENAI_*` values. A local endpoint may accept an empty key. These values belong in each instance's environment file and are not inherited from the root environment. Never place credentials in guild YAML.

Contextual interpretation and guarded reaction preflight use the explicitly configured decision adapter, otherwise the reply provider's structured route (including its configured summary-model override). The older `chat_completions` adapter can fall back to that reply route within the existing deadline; native `decisions` mode has no generative fallback. Reply-route failure does not silently downgrade to utility. Startup logs identify the effective source/model and endpoint. Run `eval:contextual -- --live --instance <instance>` for that actual selection; `--provider-role utility` and `--provider-role reply` are explicit synthetic comparisons. The measured Pinecone utility failed semantic acceptance, while its reply route passed after prompt corrections. Validate each instance before activation; see the [current release evidence](contextual-participation-release-2026-10-21.md).

Deploy slash commands through the existing command deployment procedure to expose `/settings-character` and `/character-eval`. The same registry supplies the admin panel, English, Traditional Chinese and Japanese descriptions, validation and access policy.

## Enable a small pilot

1. Choose one disclosed chatbot channel and a fictional persona. If using a real person's persona or examples, obtain their consent first. Explain that enabled channel history includes other participants' messages in provider requests.
2. Enable only `character.evaluation` first. Run interview probes and collect baseline flags. Evaluation can work with the character master switch off.
3. Enable the character master switch (`/settings-character master`) and individual modules. Start with voice and natural recall; then canon with `freeze:true` while reviewing its ledger. Relationship impressions require memory sharing. `/settings-character status channel:<channel>` explains module dependencies.
4. Enable conversation context separately with `/settings-character context enabled:true`; it is the only channel-history switch. A reply reads up to 40 recent messages (`messages`, 8–48) within a 12,000-character budget (`budget`, 2,000–24,000). A decision about whether to speak reads 10 (`decision-context`, 5–20). Running summaries default off. Memory exclusions, utility/D&D ownership and member access still control live delivery.
5. Use preview as a trial run before turning optional participation on live. Participation preview (`/settings-participation preview`) is off by default; turn it on for the pilot, and a channel or thread can override it through `/settings-participation channel preview:`. In preview, follow-ups, joining, name replies and reaction-triggered replies are logged in the bot logs instead of sent; @mentions, replies to the bot and bare pings always send. The thoughts module has its own separate `shadow` control. Thoughts require context, a decision capability and participation. The former addressing module and include-others control are retired; stored values remain read-compatible and cannot disable mandatory recipient policy. Context boundary decisions apply only to legacy history. Enable live behavior only after reviewing mistaken interruptions and wrong-person responses.
6. Turn on follow-ups (`/settings-participation follow-ups enabled:true`) only with context. The balanced preset allows 10 bot replies per exchange and 30 per channel per ten minutes; two minutes of inactivity ends an exchange. `follow-ups per-exchange`, `per-10-minutes` and `interval` adjust the caps. Joining conversations (`joining`) needs its switch and each channel on its list, and keeps stricter cooldowns under `pacing`. `reset-limits` returns every custom number to the activity preset. Both share guild admission and concurrency.
7. Consider callbacks, split messages, mood and fictional daily sketches separately. Daily sketches require canon and explicit acceptance of fictional daily life. Split messages default to one with no added delay.

Each module stores only its applicable controls. Voice defaults to trim; opt-in regeneration applies only to severe casual length/Markdown violations. Canon shares the post-reply personal extraction call and applies separate evidence rules. Semantic consistency across all slots is model-assisted, with a conservative local polarity check; human review is still needed.

Stored configuration uses `character.enabled`, `character.modules.<module>`, `character.context` and `character.channelOverrides.<channelId>`. Overrides can disable guild-enabled modules/context; they cannot activate guild-disabled modules. Switching the master or a dependency off invalidates pending influenced output. Direct/name-triggered replies keep their original memory snapshot across normal background learning and mood expiry; optional contributions revalidate context. Explicit forgetting still invalidates affected in-flight turns. Stored records remain available to authorized management until expiry or explicit clearing.

## Inspect, correct and forget

`/settings-character ledger` lists, edits, deletes or clears canon, mood or daily-sketch records. Choose a channel to see channel-scoped mood. The canon freeze stops new automatic learning while retaining existing entries. Owner personality/lore take precedence; changing the persona hash prevents use of old generated identity data.

Members can inspect and forget facts and relationship impressions through `/memory`. Impressions cite their supporting facts and provenance. Forgetting/correcting a supporting source or narrowing its channel visibility makes the old impression ineligible. Tone and teasing preferences come from fresh user customization, never from inferred consent. The memory settings group exposes character retention; it does not delete ordinary explicit facts.

Callback state stays on an ordinary event fact. Follow-ups need an explicit dated self-report, eligible provenance, current activity and access, an enabled module and a persistent daily guild quota. They ask how the event went without asserting it happened. Date normalization runs once per revision after a conditional planning reservation; unresolved dates wait for a revised fact, and transient normalization failures wait 30 minutes. The original eligible event message is the reply target; if unavailable in this channel, delivery is standalone rather than linked to unrelated activity. Pending claims expire; confirmed sends keep the Discord message ID. A timeout/crash after sending begins becomes `uncertain` and is not retried automatically. Known failures before delivery use bounded backoff, at most three attempts and a three-day callback age. Correcting or forgetting the event cancels an old pending revision; completed events are not repeated. Operators can inspect the event's `structuredValue.callback` in the database when investigating an uncertain outcome.

## Human review

Admins can use the **Felt like a bot** message command, or `/character-eval flag message:<id> category:<category>`, on recorded bot chat messages. Categories cover wrong person, assistant tone, timing, contradiction and reply length. The message command saves `other`; the slash command provides the specific category. Functional command output is not a chat review target.

`/character-eval probes` generates seven interview answers privately without tools, search, images or memory writes. `/character-eval pair question:<question>` generates a baseline/candidate pair randomized as A/B; `/character-eval label` saves a human preference. `/character-eval export` exports review metadata and synthetic outputs. Review data is separate from memory, bounded to 500 records and 30-day retention. Optional scheduled probes default off and run daily by default (minimum configurable interval: 60 minutes). Batches obey evaluation cooldowns and share guild concurrency; each answer reserves one unit of the optional-call budget, so an interview costs seven and a blind pair costs two. These synthetic pairs do not replace comparisons from real conversations.

Record reviewer judgments for identity consistency, correct speaker, stale/forgotten facts, welcome callbacks, appropriate timing, substantive completeness and truthful bot identity. Add consented regression fixtures for failures. Measure provider cost and interruptions as diagnostics. Do not use a judge-model score or message volume as the success criterion.

## Offline chronological replay

Use a consented, anonymized JSON manifest with pseudonymous numeric Discord IDs, never real member identifiers:

```json
{
  "consented": true,
  "anonymized": true,
  "turns": [
    {
      "timestampMs": 1791936000000,
      "channelId": "200000000000000001",
      "speakerId": "300000000000000001",
      "message": "Are you a bot or a real person?",
      "expected": ["honest-bot", "no-invented-past"]
    }
  ]
}
```

```sh
npm run eval:character-replay -- --fixture replay.json --persona personality.md --settings character-settings.json --output review.json
```

The settings file is the `character` object only. The runner requires configured chat providers, makes real provider calls, uses a new temporary SQLite database and an injected chronological clock, and does not connect or post to Discord. It feeds turns through the real conversation/memory/module services with tools/search/images disabled. The output is a human-review artifact, not a computed believability score. The temporary database location is printed for inspection; it is not the live bot database. On PowerShell installations that consume forwarded npm flags, invoke the equivalent `node node_modules/tsx/dist/cli.mjs src/scripts/replay-character-conversations.ts ...` directly.

Complete a week of probes and one-channel live review before broad rollout. PostgreSQL contract execution needs `MEMORY_TEST_DATABASE_URL`; SQLite tests do not establish live PostgreSQL behavior. No live pilot or real transcript replay is implied by the local implementation checks.

## Simple participation trial (Phase 1)

The simple contract asks one question per eligible optional turn (reply, react or ignore, plus an emoji) of a small fast model. Phase 1 is a trial run: the decision is logged and nothing optional is sent, whatever the preview switch says. @mentions, replies to the bot and bare pings are unaffected. Design and rollout criteria: `docs/simple-participation-decision-plan.md`.

1. Route (instance): keep `PARTICIPATION_DECISION_CONTRACT=legacy`. Native `DECISION_MODE=decisions` uses `/v1/decisions`; a `DECISION_MODEL` with `chat_completions` uses that model with `DECISION_REASONING_EFFORT` if set; otherwise the reply model runs at `CHATBOT_DECISION_REASONING_EFFORT` (default: the summary effort, `low`). The utility model is never a fallback. Startup logs the chosen route as "Simple participation decision route".
2. Pilot one channel: `/settings-participation channel channel:<channel> decision-contract:simple`, with follow-ups and/or joining on and the channel observed. `/settings-participation policy` shows the effective contract, the thresholds and the route. Turn callbacks off there if the trial must stay quiet: `/settings-character channel module:callbacks enabled:false`.
3. Inner thoughts (optional): `/settings-character thoughts` with `enabled` and `shadow` off lets a thought held for an ignored message be offered to the next decision from the same person. Leave `shadow` on to only log thoughts.
4. Read the logs: `Simple participation decision` (info, `event: chat.simple_decision`) has the kind and basis, proposed action, emoji, score, admission outcome (`trial_not_sent` when the model chose to act), route, latency, usage and the thought fields. Skipped turns are `Simple participation exclusion` (debug, `event: chat.simple_exclusion`), with the reason. Neither contains message content.
5. Roll back by setting the channel (or server) `decision-contract` to `legacy` or `inherit`; no restart is needed.

Limits of the trial: a turn the earlier admission stage does not route (for example a message the old rules would not treat as a follow-up or an allowed joining channel) never reaches the simple decision, and delivered follow-ups, exchange accounting and the restart wait belong to Phase 2.
